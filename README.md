# certified.app v2

Work in progress: the rebuild of [certified.app](https://certified.app) as a reference implementation of the Hypercerts protocol and API. The current production app lives on `main` and `staging`; this branch (`v2`) starts from a clean slate.

So far: public pages backed by live data from the [Hypercerts API](https://docs.hypercerts.org/reference/services/hypercerts-api), sign-in, and editing your own profile or an organization's (signed writes, organizations through the Certified Group Service).

## Running it

```bash
pnpm install
pnpm dev           # starts Next.js
pnpm build         # production build
pnpm typecheck
pnpm lint          # Biome lint
pnpm format:check  # Biome formatting, without changing files
pnpm format        # apply Biome's formatting
pnpm test          # unit tests (Vitest)
pnpm lex:check     # the generated getServiceAuth binding matches lexicons.json
```

Node 24 (see `.nvmrc`). Tooling follows the Hypercerts SDK repository: Biome with the same rules and formatting, pnpm, TypeScript 7, Node 24. The API defaults to production, `https://api.hypercerts.dev`; set `HYPERCERTS_API_URL` to use another deployment.

### Signing in locally

Sign-in needs Valkey, the open-source fork of Redis. `docker compose up -d` starts it on `127.0.0.1:6379`; copy the `VALKEY_URL` and `PUBLIC_URL` lines from `.env.example` into `.env.local`. In production, `VALKEY_URL` is any managed Valkey (or other Redis-compatible) provider's `redis://` or `rediss://` connection string; without it the app uses `REDIS_URL`, which a Redis database from the Vercel Marketplace (Upstash, Redis Cloud) sets when connected to the project. Without an https `PUBLIC_URL`, the app is an atproto loopback client: open it at `http://127.0.0.1:3000` (not `localhost`), because the authorization server redirects back there. From another machine, forward the port (`ssh -L 3000:127.0.0.1:3000 <host>`) and use the same URL. Certified's sign-in page can't read a loopback client's metadata, so locally it offers only the email code; "Sign in with Atmosphere" and Google appear on a deployment.

Writing also needs `CREATED_VIA_SIGNING_KEY` (see `.env.example` for generating one); without it, saves fail rather than go out unsigned. `pnpm test` runs the unit tests.

## Adapting this app

Certified-specific choices a copy for another Hypercerts app would change:

- **Identity:** the OAuth `client_name` and logo (`src/lib/auth/oauth-client.ts`), the cookie names (`certified_session`, `certified_sign_in`, `certified_acting_as`), and wording such as "signed by certified.app" and "View on Certified".
- **Services:** email sign-in through Certified's PDS (`CERTIFIED_PDS_URL`), organizations on the Certified Group Service (`CGS_URL`, and `CGS_DID` if the deployment sets its own service DID), and the app's `createdVia` signing key (`CREATED_VIA_SIGNING_KEY`), which names the app in every record it writes.
- **Content:** Explore's Featured, the projects Ma Earth gave its "Ma Earth Round 3" badge, with their activities and organizations (`FEATURED_BADGE` in `src/lib/hypercerts/queries.ts`); the featured profiles on the landing page (`FEATURED` in `src/components/landing/explore-profiles.tsx`) and the prerendered sample account and project (`generateStaticParams` in the account and project pages).
- **Hosting:** the sign-in rate limit keys on the client IP from `@vercel/functions` (`x-real-ip`). Behind another proxy, check that header is set, or every visitor shares one limit. Preview detection uses `VERCEL_ENV` and `*.vercel.app`.

## How it is put together

- **Next.js 16 App Router with Cache Components.** Pages are Server Components. Public data is read through cached functions (`'use cache'` with the `public` profile: revalidated on the server every minute, reused by the browser for five minutes, which keeps it in the shell every link prefetches). Dynamic routes render a static shell and are then cached per URL (ISR), so repeat visitors are served from the cache.
- **One data module.** `src/lib/hypercerts/queries.ts` is the only code that talks to the API. It calls XRPC endpoints through an [`@atproto/lex`](https://www.npmjs.com/package/@atproto/lex) `Client`, which returns responses typed from the API's lexicons, and maps them to plain view models (`src/lib/hypercerts/views.ts`). Endpoint definitions and view types come from [`@hypercerts-org/api`](https://www.npmjs.com/package/@hypercerts-org/api), and the record types those views embed from [`@hypercerts-org/lexicon`](https://www.npmjs.com/package/@hypercerts-org/lexicon). When the Hypercerts SDK ships its read layer, only this module should change.
- **Bindings.** All three packages are generated from the lexicons in their own repositories and installed from npm: `@hypercerts-org/api`, `@hypercerts-org/lexicon`, and `@hypercerts-org/certified-group-service` for the Certified Group Service. Keep their versions in step: `@hypercerts-org/api` declares the `@hypercerts-org/lexicon` range its types are built against, and all share one `@atproto/lex`. The only binding generated here is `com.atproto.server.getServiceAuth`, which calling CGS needs and no package ships: `lexicons.json` installs it from the network with `lex install`, recorded with its CID, and `lex build` generates `src/lexicons/` (`pnpm lex:install`, `pnpm lex:build`).
- **Who is viewing.** `src/lib/auth/dal.ts` says who is signed in (`getUser()`, cached per session). What a page shows for them is decided from cached data, never by a round trip per component: your memberships (`getMemberships()`, `src/lib/memberships.ts`: Valkey, then cached per session, an OAuth restore and CGS call only on a miss), whom you act as (`getActingAs()`), whether you may edit an account (`mayEditAccount()`), and whether you may open a workspace (`workspaceAccess`, `src/components/workspace-access.tsx`). Each is computed once per request (React `cache`). These decide only what pages show; writes check CGS live (`isMember` / `canEdit`). A workspace's layout shows why you can't open it, and every workspace page and nested layout also checks, since a layout alone doesn't keep a page's data out of the response.
- **Prefetching.** Tabs, the sidebar and other short navigation use `<Link prefetch>`: the destination's cached content arrives before the click. Links in lists and grids (and every design-system link) use `IntentLink`, which prefetches the shared shell for every link and the content on hover, focus or touch. Every click shows at once: tabs and nav items mark themselves pending (`LinkPending`, Next's `useLinkStatus`) and each section renders co-located skeletons inside `<Suspense>`.
- **Design system.** Components come from [`@hypercerts-org/ui-react`](https://github.com/hypercerts-org/hypercerts-design) with the Certified theme (`data-hc-theme="certified"`). The theme names its fonts, Inter and Noto Serif, but ships no files: `next/font` self-hosts them (`src/app/layout.tsx`) and `src/app/globals.css` points the theme's font variables at them. Otherwise `globals.css` adds layout and the styles of the app's own navigation. Headings are the toolkit's `Heading`: `PageTitle` (display-2) for each page's one h1, `heading` for every heading below it; labels are `Eyebrow`. Placeholders for writes not built yet are `ComingSoonButton`. What the app needed from the toolkit and built itself is listed in `docs/toolkit-gaps.md`; app CSS never reaches into a toolkit component except in that file's "bridged" rules.
- **Maps.** A place on a profile is drawn with [MapLibre GL](https://maplibre.org) from [OpenFreeMap](https://openfreemap.org)'s vector tiles (OpenStreetMap data; no key, account or fees), in `src/components/location-map.tsx`. MapLibre loads only in the browser, when a map is on the page. The point comes from the account's location record (`toPlace` in `src/lib/hypercerts/views.ts`), which arrives with the organization (or, for a record that keeps it in a blob, from the account's server, `src/lib/blobs.ts`). The short place name in the profile's header, "Corvallis, United States", comes from that point through [Nominatim](https://nominatim.org), OpenStreetMap's geocoder (`src/lib/geocode.ts`): once per point, cached for good, a second apart, as its usage policy asks.
- **Tiles.** Each tile in `src/components/tiles.tsx` fetches its own data and streams in behind its own Suspense boundary, so a page can show, hide or reorder tiles independently.
- **Sign-in.** The server is the OAuth client (`@atproto/oauth-client-node`) and keeps each account's tokens in Valkey (through the standard `redis` client, since Valkey speaks the Redis protocol), so it can later write and sign records for the user. The browser gets only a session cookie: a random token whose SHA-256 hash keys the session in Valkey. `src/lib/auth/dal.ts` is the only way to ask who is signed in (`getUser()`, a private cache per the Next.js guide on authentication with Cache Components, no PDS calls) or to get a session for PDS calls (`getOAuthSession()`, Server Actions and Route Handlers only, refreshes tokens). Sign in sends the browser straight to Certified's PDS (`CERTIFIED_PDS_URL`), whose own page offers an email code, Google, or a handle on any AT Protocol server; a browser already signed in there comes straight back. A handle on another server is handed back to `/oauth/handle-login`, which starts the sign-in at that account's own server. The Sign in buttons are plain HTML forms posting to the `/oauth/sign-in` Route Handler, which answers with a redirect, so the browser leaves as after any form, with no waiting state. Sign-out is a Server Action; the callback and the hand-off are Route Handlers. The header's account area reads the session inside a Suspense boundary, so public pages keep their cached shell.
- **Acting as.** The account menu lists you and every organization you belong to on the Certified Group Service. Choosing one calls a Server Action (`switchActingAs`) that sets the choice as a cookie (`certified_acting_as`), so Next.js re-renders the page as that identity in the same round trip, and every later request renders as it too; a toast (Sonner) offers Go to workspace and Undo. `getActingAs()` (`src/lib/acting-as.ts`) falls back to your own account once the membership is gone. The choice only decides what pages show (header, `/workspace`): writes never read it (see Organizations).
- **Sign-in safeguards.**
  - The OAuth client (PAR, PKCE, DPoP, issuer checks) and its outbound fetch (atproto's `safeFetchWrap`: no private addresses, size-capped responses) are atproto's own; the app adds stores, a lock and the session cookie.
  - A sign-in is bound to the browser that started it: a nonce in a cookie must match the one in the OAuth state (RFC 9700 4.7), so nobody can sign a victim in to their own account with a callback link. The cookie also keeps the page to return to, so a handed-over sign-in still returns there.
  - Nothing starts a sign-in on a plain link: Next.js prefetches links, so the Sign in buttons post a form, and `/oauth/handle-login` is only reached through Certified's hand-off.
  - A Valkey lock serializes token refreshes across server instances, since a refresh token can be used once and a concurrent refresh would get the session revoked.
  - Every Valkey failure becomes `StoreUnavailableError`: a Valkey outage fails requests but never signs anyone out.
  - Starting a sign-in is limited to 10 per IP address per minute. Cookies are `__Host-` prefixed over https.
  - No route may be framed by other sites: every response sends `frame-ancestors 'none'` and `X-Frame-Options: DENY` (`next.config.ts`).
  - All browsers signed in to one account share its OAuth session; signing out revokes the tokens only when the last of them signs out.
- **Writes.** Writes supported by `@hypercerts-org/sdk` (activities, projects, organizations, follows, badge definitions/awards/responses, list creation) go through `src/lib/hypercerts/sdk.ts` (`sdkContext()`, reusing the OAuth client's SSRF-safe `identityResolver`). Remaining updates and deletes (profile updates, list edits/items/deletes, endorsement revocation) go through `src/lib/hypercerts/writes.ts` with compare-and-swap on CID (`swapRecord`) and `createdVia` signatures. Outcomes are stored, refused (a 4xx answer: nothing written) or unknown (`WriteOutcomeUnknownError`, `PartialWriteError`, `WriteResultMismatchError`, or 5xx/no answer: the user is asked to reload; never retried automatically). Preview deployments (`VERCEL_ENV === "preview"`, `*.vercel.app`) refuse all writes via `assertWritesAllowed()`.
- **Organizations.** Every write names its target repository explicitly (in the URL, form, or action input); the session's acting-as cookie only decides what pages show, so a tab opened before a switch still writes as what it showed. Organizations live on the Certified Group Service (CGS, `src/lib/cgs.ts`), which holds their credentials and checks each member's role. The app calls CGS directly, as its integration guide recommends, with a single-use service-auth token from the user's PDS per call (`aud` `${CGS_DID}#certified_group_service`, `lxm` the method, the organization in `repo`). Admins and owners may edit an organization's profile here, and CGS records each write, with the user, in the organization's audit log. CGS itself only limits `app.bsky.actor.profile` to admins: for `app.certified.actor.profile` it checks membership and who authored the record, so until CGS treats it as a profile too, the admin rule holds in this app only. Reads come from the organization's own PDS, resolved and fetched through the OAuth client's SSRF-safe resolver, and CGS `putRecord` enforces compare-and-swap via `swapRecord`.
- **Record signing.** Records written through `writes.ts` carry an `app.certified.signature.defs#createdVia` signature, made by `src/lib/atproto/created-via.ts` with the SDK record-signing spec's `RecordSigner` contract (SDK writes will sign as soon as `@hypercerts-org/sdk` accepts `RecordSigner`). Deployed, the key is published in the app's `did:web` document at `/.well-known/did.json` (fragment `#created-via`, as on the current certified.app) under `did:web:<PUBLIC_URL host>`. Signing and writes never run on preview hosts, so writes fail there instead of mutating live repositories or producing unverifiable signatures. Locally the key is a `did:key`. Unit tests verify signatures with the lexicon README's own procedure and encoder, including after the JSON round trip to the PDS; after each signed write the stored CID is checked against the signed record.
- **Showing your own writes.** The index is the one source of what pages show. A write's Server Action writes (with the Hypercerts SDK or `writes.ts`), then waits up to 3 s for the index to show it (`src/lib/hypercerts/index-wait.ts`; it should take a second or two), then expires every cache tag the write changes with `updateTag`, so the action returns with the page re-rendered from the index, and every page after shows it too. Nothing is kept in the browser. A form is disabled, with a spinner on Save, until the action returns. Toggles such as Follow and Endorse show their new state on click (React's `useOptimistic`, held until the action's refreshed page arrives); if the index was slower than the wait, they keep what was written until the page shows something new, and the other pages catch up as their cache refreshes. This is the pattern for every write on the site.
- **Follow & Endorse.** Profile header Follow (`src/lib/hypercerts/follow-actions.ts`) and Endorse (`src/lib/hypercerts/endorsement-actions.ts`) write with the Hypercerts SDK (passing the explicit `repo` rendered on screen: your own repository, or an organization's through CGS). The SDK is not on npm yet: it is installed from `vendor/` (see `vendor/README.md`).
- **Also on.** A project's or an account's page on other apps that show the same records (Ma Earth, GainForest, Good Market). Part of it isn't read from the protocol, so all of it lives in `src/lib/also-on/` behind one server function, `getAlsoOn`, with its data, refresh script and app icons; the page shows it with `src/components/also-on.tsx`. Good Market's page address comes on its "Good Market Approved" badge; GainForest's addresses are built from the record's IDs and checked against its sitemap (read daily); Ma Earth's are looked up in `maearth-pages.json`, which `node src/lib/also-on/update-maearth-pages.mjs` rebuilds from its sitemap. That table is a stopgap until Ma Earth writes its page addresses on its badges, as Good Market does.
- **Load more.** The first page is server-rendered; later pages come from the GET route handlers through TanStack Query's `useInfiniteQuery`, which call the same cached functions and send `Cache-Control: public, s-maxage=60, stale-while-revalidate=600`. The client deduplicates by URI across pages.

## Spike findings

Known challenges and our current answers. These feed the architecture notes and upstream issues.

1. **`@atproto/lex` 0.4.2 generates broken imports** when a query lives under a record NSID (`org.hypercerts.collection.getCollection`, `app.certified.location.getLocation`): it emits `./.defs`. The workaround now lives in `@hypercerts-org/api`'s generator, not in the app. Reported upstream as [bluesky-social/atproto#5738](https://github.com/bluesky-social/atproto/issues/5738), with a fix ready.
2. **Turbopack does not resolve the `.js` import specifiers** that `lex build` generates by default to `.ts` files. The API and record bindings are compiled JavaScript from npm, so this only affects the generated CGS bindings, which are built with `--import-ext ""` (extension-less imports, one of lex's own options).
3. **Indexed records do not always match their lexicons.** About a quarter of indexed activities fail lexicon validation: plain-string descriptions, union values without `$type`. Most were invalid when written; about 119 were valid and broke when the lexicon changed. With lex's default response validation, one such record fails the whole list request, so reads skip response validation and the mappers in `src/lib/hypercerts/views.ts` read descriptions and blob references defensively; writes validate strictly. Proposed resolution (index-time validation, repair only what our lexicon changes broke): [TECH-791](https://linear.app/hypercerts/issue/TECH-791).
4. **API views carry no handle.** Profile and actor views include the DID but not the handle. The app resolves handles itself (`src/lib/identity.ts`: the AT Protocol identity resolver, checked both ways, SSRF-safe, cached for hours) and attaches them to every account card, so links go to `/{handle}`. A profile is shown only at a handle verified both ways: the API resolves a handle one way only. An API field would remove the lookups.
5. **Images are blob references.** The API returns no image URLs, so the app serves every image (avatars, activity and project images) through the Bluesky CDN (`cdn.bsky.app`), which fetches the blob from the account's PDS for any record, resizes it and caches it. The app uses the 128px `avatar_thumbnail` size (about 6 KB, where an original may be up to 5 MB). This depends on Bluesky infrastructure that isn't offered to other apps; the long-term fix is image URLs from the API, served by Hypercerts' own image service.
6. **`'use cache'` is per-instance memory on serverless.** Shared caching for public pages comes from Cache Components' ISR and from CDN headers on the GET route handlers, not from `'use cache'` alone.
7. **Not-found inside a streamed boundary returns HTTP 200.** An unknown account renders the not-found UI, but the status has already been sent. Acceptable for the spike; revisit before launch (for example, resolve the account before streaming).
8. **The app has to choose its slice of the data.** The network contains test records, odd definitions and anything else anyone publishes; that is normal on AT Protocol and not something this app tries to fix. A client shows only the data relevant to it. For example, a test account ("Karmas Test Org") is the second-largest badge issuer, so the landing page features a hand-picked list of issuers rather than ranking by award count. The current app also hides test records with quality labels, which the API does not expose for filtering. How v2 chooses its slice beyond hand-picked lists is not decided.
