## [HIGH] correctness-1 — Default "Confirmed by" filter silently hides third-party-only funding receipts while the count still includes them

This affects the activity detail Funding tab (activity-detail.tsx filteredFunding), the /explore Funding list (ResultsArea, explore.tsx:1879-1887), and the All view (explore.tsx:1218-1226). ## [HIGH] performance-1 — Funding list issues an uncached getRecord per row for the "for" activity (N+1, no dedupe)

## [MEDIUM] security-1 — /api/ens is an unauthenticated, unthrottled third-party proxy — egress-quota / IP-reputation abuse surface
- **dimension:** security · **fix:** trivial · **confidence:** high · **orig severity:** medium
- **location:** `src/app/api/ens/route.ts:34-68`
- **problem:** The new ENS reverse-resolution route fans out a server-side fetch to the third-party ensideas API on every request, but unlike every other third-party-proxy route in this repo it has NO authentication and NO rate limit. The address is strictly validated (ADDRESS_RE) so there is no SSRF/open-proxy-to-arbitrary-host, but an attacker can still flood the endpoint with distinct valid-but-random addresses (the 16^40 address space means each request is a fresh upstream call that the 24h edge cache cannot collapse) to (a) burn the app's egress against ensideas, (b) get the app's egress IP rate-limited or banned by ensideas (degrading ENS resolution for all real users), and (c) drive serverless invocation/cost. The sibling /api/geocode route documents exactly this threat ('anonymous traffic can otherwise burn through our [upstream] quota and rate-limit our egress IP for legitimate users') and mitigates it with getSessionDid() + enforceRateLimit; /api/ens omits both. The indexer proxy added in the same range correctly uses clientIp()+makeLimiter+enforceRateLimit.
- **evidence:** export async function GET(request: Request): Promise<NextResponse> {
  const address = (new URL(request.url).searchParams.get("address") ?? "").trim()
  if (!ADDRESS_RE.test(address)) { ... }
  // no checkCsrf, no enforceRateLimit, no auth gate
  const res = await fetch(`${UPSTREAM}${address}`, ... )
- **fix:** Add an IP-scoped rate limiter mirroring the other read proxies, e.g. at module scope `const LIMITER = makeLimiter("ens", 120, 60)` and at the top of GET (after address validation) `const denied = await enforceRateLimit(LIMITER, clientIp(request as unknown as NextRequest)); if (denied) return denied` (switch the handler signature to NextRequest so clientIp works). Auth-gating like /api/geocode would be even stronger, but ENS rows can render in unauthenticated/landing contexts, so a per-IP limiter is the minimal fix.
- **verifier:** Confirmed in the review range. src/app/api/ens/route.ts (added in commit 7f586c2, within b6e2a15..HEAD) exposes GET(request: Request) that validates address against ADDRESS_RE then server-side fetches https://api.ensideas.com with NO auth, NO CSRF, and NO rate limiter. This is a genuine anomaly: every other read proxy in the repo enforces a limiter — /api/geocode (session gate + makeLimiter), /api/indexer added in the same range (clientIp+makeLimiter("indexer-proxy",240,60)+enforceRateLimit), and crucially /api/resolve-handle which is the unauthenticated per-IP pattern the finding recommends (makeLimiter("resolve-handle",100,60)+enforceRateLimit). The geocode docstring quotes the exact threat ("anonymous traffic can otherwise burn through our quota and rate-limit our egress IP"). The threat model is sound: the 24h edge cache only collapses identical addresses, and the error path returns no cache headers (line 66), so distinct random valid addresses each miss cache and fan out fresh upstream calls — burning egress, risking egress-IP rate-limiting/ban by ensideas (degrading ENS for all users), and driving invocation cost. No SSRF because the regex blocks arbitrary hosts. The recommended fix is correct and safe: makeLimiter/enforceRateLimit/clientIp signatures match exactly, clientIp requires NextRequest so the handler signature must switch (as all siblings do), and enforceRateLimit fails open on Redis errors so it won't break resolution. Auth-gating is correctly rejected because ENS rows render via resolveEns() in explore/funding contexts that can be unauthenticated. Severity medium is fair (slightly generous given Vercel platform DDoS backstop and no SSRF, but it's a real abuse surface inconsistent with the repo's own documented pattern and trivially fixable). Fix is ~5 lines copyable from /api/resolve-handle: trivial. Only minor caveat: the finding suggests max 120/60 vs resolve-handle's 100/60 — the exact number is a judgment call, not load-bearing.
