Certified migration plan

Magic Indexer → Hyperindex

A staged plan for removing Certified’s Magic Indexer dependency while keeping the app’s existing read APIs stable. The sequence moves from least invasive and easiest to verify to the highest-effort product-specific replacement work.

Planning rule

This is not a PDS-to-indexer migration. PDS and CGS remain write sources of truth. The goal is to replace the Magic Indexer-compatible read proxy with Hyperindex-backed operations.

Target architecture

Keep the app-facing operation contract stable at first. Replace the implementation behind each operation group one stage at a time. Components should not need to know whether a response came from Magic Indexer or Hyperindex while the migration is in flight.

Migration invariant

  • Do not move writes. Hyperindex is the read model. PDS and CGS stay authoritative for writes, swaps, deletes, and edit prefill.
  • Keep operation names stable. Port the server-side query behind each operation before changing client hooks.
  • Dual-run where possible. In dev/staging, compare Magic and Hyperindex results for a small sample before flipping production.
  • Home feed is special. Magic’s followerEvents and HydrateFeedPage are product resolvers, not simple typed collection queries.

Effort ladder

The order below intentionally starts with low-blast-radius reads that are easy to assert, then moves into broader UI surfaces, joined data, and finally Magic-only custom feed behavior.

Stage 0 · least invasive

Foundation and safety rails

Effort S · Risk low

Scope

  • Add Hyperindex endpoint config.
  • Keep /api/indexer and operation names.
  • Add schema smoke checks for production/staging Hyperindex.
  • Add optional dev parity logging for selected operations.

Why first

It proves connectivity, schema availability, timeout behavior, and deployment config without changing any user-visible data yet.

Acceptance

  • Build passes.
  • Proxy rejects unknown operations exactly as before.
  • Hyperindex schema check confirms required root fields.

Effort S · Risk low

Stage 2

Port activity read operations

Effort M · Risk medium

Activities power Explore, profile Activities, search snippets, and detail fallback. Keep the helper API stable and translate Magic’s convenience args into Hyperindex where inputs.

  • where.did.eq for authored profile tab.

  • labels/excludeLabels → external label predicates.
  • authorLabels → author label predicates.

Stage 4

Port follow graph reads

Effort M · Risk medium

Followers are a straightforward typed-collection migration via appCertifiedGraphFollow. Keep follow/unfollow writes unchanged. Do not include home-feed event generation in this stage.

Stage 5

Port actor and organization lookup

Effort M/L · Risk medium

These operations feed workspace actor pickers, global search support, organization filters, and quality-filtered account lists. They should happen after the simpler record lists because label semantics and profile completeness matter more here.

NetworkActors · NetworkActorsByKind · OrganizationDids · OrganizationDidsByLabel · NetworkActorsByDids · OrganizationDidsForSet · DidsByKindInSet

Stage 6

Port endorsement reads

Effort L · Risk medium/high

Endorsements are typed, but Magic currently provides useful joins such as issuer profile and latest response. Before flipping, confirm Hyperindex exposes equivalent fields or add a compatibility join/fallback.

Operations

ReceivedEndorsements
EvaluatorEndorsements
AllEndorsements
EndorsementDefs
EndorsementClosure

Parity checks

  • Rejected responses stay hidden where expected.
  • Default endorsement vs list endorsement semantics stay intact.
  • Issuer/subject display still avoids N+1 regressions where possible.
  • Endorsement graph counts match the public graph page.

Stage 7

Port funding reads

Effort L · Risk high

Funding uses orgHypercertsFundingReceipt, but the UI depends on role semantics, confirmation/provenance display, and post-write indexer lag handling. Port after endorsements so shared actor and profile resolution patterns are already stable.

Stage 8 · hardest

Replace Magic-only home feed resolvers

Effort XL · Risk high

Hyperindex production exposes recordTimeline, but not Magic’s followerEvents or HydrateFeedPage. This should be the last substantive migration because it changes the feed’s data model, pagination, and hydration strategy.

Option A

Use recordTimeline with followed DIDs, then hydrate per collection client/server side.

Option B

Add a Hyperindex resolver equivalent to followerEvents and keep the app contract close to today.

Option C

Temporarily keep Magic only for home feed while every typed operation moves to Hyperindex.

Stage 9

Remove Magic Indexer completely

Effort M · Risk release

Remove

  • Magic fallback URL.
  • Magic-specific docs/comments.
  • Operation branches no longer used by any caller.
  • Compatibility code for Magic-only label/search args.

Release gate

  • No production requests to Magic for a full observation window.
  • Staging parity suite passes against Hyperindex only.
  • Feature smoke checks pass: Explore, profile tabs, endorsements, funding, home feed.
