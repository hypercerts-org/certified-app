Option 3 — the GitHub model no persona mode · per-action identity · orgs can endorse

You are always you in the chrome, your feed, and your profile. There is no "acting as" mode to enter or forget. Identity is chosen per action via a split button: the primary side acts as you by default; the chevron opens a small menu of the orgs you own or admin. The default is always You (never last-used), so the sticky-mode bug class is gone by construction. Because endorsing is high-stakes and core to Certified, choosing a group as the endorser triggers a confirm that names all three parties. Managing a group happens on the group's own page.

How it behaves
Split button on the action itself: primary acts as you; the chevron picks a different endorser for this one action. Identity stays on the button (Facebook's pattern, not LinkedIn's misplaced corner).
Default is always You. The menu resets to you each time, so you can't drift into endorsing as the wrong org.
Only orgs you own/admin appear, with the role shown. The server re-checks the role on write.
Follow as org is one click (low-stakes). Endorse as org gets the confirm, because it is the product's core trust record.

What it takes to ship (grounded in the backend trace)

Unlike Options 1 & 2, this needs real backend work, because "endorse as org" does not exist yet. The UI above is the target; here is the gap.

Follow as org ~50% built
Have: group follow create (POST /api/groups/[did]/follow, createFollow via writeToRepo targetDid).
  • Add DELETE to the group follow route (it is POST-only today, so a group can't unfollow).
  • deleteFollow must take a targetDid and route via writeToRepo (currently hardwired to the personal proxy).
  • Thread targetDid into the 2 unfollow call sites; wire the profile Follow button's actor picker.
Endorse as org 0% built
Endorse is hardwired to the personal DID; no group badge route exists, and the XRPC proxy blocks group writes (repo === session).
  • New group badge route (POST + DELETE for app.certified.badge.award) modeled on the follow POST + project DELETE.
  • Per-group endorsement definition: ensure an app.certified.badge.definition on the group repo (the lazy ensure can only target the personal repo today).
  • Refactor createEndorsementAward / deleteEndorsementAward to accept targetDid via writeToRepo; thread it through the 5 award call sites.
  • Revisit the "endorsements = personal-only" classification; mirror the badge.award rate-limit on the group route.
Permission is already enforceable: group writes go through createGroupAgent, which the group service authorizes for owner/admin only and rejects for members. The picker just mirrors that role gate in the UI.
Accountability: the public endorser is the group DID, but the authoring admin's DID is retained in the group's audit log, so "who endorsed as Acme" is always answerable.
