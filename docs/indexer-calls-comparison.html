certified-app → Magic Indexer vs. the live Hyperindex

Every request the app makes to the Magic Indexer, the feature it powers, whether the deployed Hyperindex can serve it, and how to bridge any gap. The Hyperindex column is now verified by live GraphQL introspection of https://api.indexer.hypercerts.dev/graphql (not inferred from code comments).

Verified against the live schema on 2026-06-10. I introspected the deployed Hyperindex (POST .../graphql with __schema / __type queries) and read its Query root fields and every relevant *WhereInput + filter-operator type. So "Hyperindex can serve?" reflects what the running schema actually exposes today. The big surprise vs. my first pass: Hyperindex is the same ATProto lexicon indexer (same types), and it has native label filtering and DID filtering — but it expresses them with different syntax than the fork, and it has a handful of hard gaps (notably it cannot filter badge awards by recipient).

Ground-truth schema facts (from introspection)

  • Present: every base lexicon connection the app reads — orgHypercertsClaimActivity, orgHypercertsCollection, appCertifiedActorProfile, appCertifiedActorOrganization, appCertifiedBadgeAward, appCertifiedBadgeDefinition, appCertifiedGraphFollow, evaluation/measurement/attachment, etc. — each with where, first/after/last/before, and sortBy/sortDirection. Plus per-collection …ByUri(uri) single-record resolvers, a top-level search(collection, query, …), and externalLabels(sources, values, activeOnly, subjects).
  • Filter operators: StringFilterInput = eq, neq, in, contains, startsWith, isNull; DIDFilterInput = eq, in; ExternalLabelWhereInput = has, none; BooleanFilterInput exists. No eqi (case-insensitive) anywhere.
  • Native labels: filter any record by label via where:{ externalLabels:{ has:[…], none:[…] } } — the fork's inline labels/excludeLabels map straight onto this.
  • Author/issuer filter: where:{ did:{ eq | in } } on every connection.
  • No uri field in any WhereInput — multi-URI hydration can't use where:{uri:{in:…}}; must fan out via aliased …ByUri resolvers.
  • Award subject is presence-only (PresenceFilterInput = isNull). You can filter awards by issuer (did) but not by recipient — so "endorsements received by DID X" has no server-side filter. (Follow subject, by contrast, is a StringFilterInput, so Followers works.)
  • Presence-only (can't match a value): activity contributors, collection items — so no "by contributor DID" and no "collections containing activity URI" filters. Badge badge/subject too.
  • No derived flags / custom resolvers: profile has no isOrganization field; and followerEvents, endorsementClosure, actorProfile(did), and the notifications service are absent.
  • Definitions: appCertifiedBadgeDefinition.where does expose badgeType (StringFilterInput) — but appCertifiedBadgeAward.where does not.

4 · Feature requests to Hyperindex (to serve certified-app natively)

Derived from the verified gaps above. Each is what the hb-agent/magic-indexer fork adds today; landing them upstream would let certified-app drop its fork and point INDEXER_URL at api.indexer.hypercerts.dev. Ordered by impact — P0 are hard blockers with no scalable client workaround.

# Request Concrete schema change Priority Unblocks / why it matters
1 Filter badge awards by recipient Make AppCertifiedBadgeAwardWhereInput.subject a value filter (DIDFilterInput / StringFilterInput) instead of PresenceFilterInput; ideally also a denormalized subjectDid field. P0 The single biggest gap. Today there is no way to ask "awards received by DID X." Unblocks the profile endorsements panel, the per-actor endorsements-received count, and the "endorsement received" notification class. No client-side workaround scales (would require scanning all awards).
2 Contributor-DID filter on activities Add a value-matchable contributor filter to OrgHypercertsClaimActivityWhereInput — e.g. contributors:{ has: $did } or a contributor: DIDFilterInput (handling the DID / strongRef / identity variants). P0 Unblocks Profile › Activities "Contributed" bucket. The contribution lexicons only expose their own author did, so there is no reverse path from a contributor to the activities they're on.
3 Reverse activity → collection containment Add an itemUri filter to OrgHypercertsCollectionWhereInput — e.g. items:{ has:{ uri: $certUri } } (promote the strongRef URI to an indexed, filterable field). P0 Unblocks the activity-detail "Projects containing this activity" section. items is presence-only today, so cross-DID containment can't be queried.
4 Personalized notifications service Host the JWT-scoped notification API (or equivalent): notifications(first,after), unreadNotificationCount, and the updateNotificationsSeen(seenAt) mutation, deriving the acting DID from service-auth. P0 Entire notifications feature (list page + nav-bell unread badge + seen-state). It's a separate component with read/write per-viewer state — nothing in the public read-only schema can stand in for it.
5 uri filter on every connection Add uri: StringFilterInput (supporting in) to all *WhereInput types, so where:{ uri:{ in:[…] } } works. P1 Collapses the home-feed HydrateFeedPage (7 kinds) and ActivitiesByUris from aliased …ByUri fan-outs back to one clean batched query per kind, and lets label filters apply on the same call.
6 Home-timeline followerEvents union Add a followerEvents(authors, kinds, sortBy, first, after) resolver: a cross-lexicon "create events by author set" stream with a single stable cursor and denormalized actor{ handle, displayName, avatarCid }. P1 The home feed. Reconstructing it from N per-lexicon queries works for page 1 but the merged-stream pagination cursor is the hard part to replicate client-side for infinite scroll.
7 badgeType filter on awards Add badgeType: StringFilterInput to AppCertifiedBadgeAwardWhereInput (it already exists on definitions). P1 Removes the client-side definition join for the trusted-evaluator expansion and received endorsements. Pairs naturally with request #1.
8 Endorsement-graph closure resolver Add endorsementClosure(viewer, degree){ accounts{ did, degree, via, issuer{…} }, truncated } (viewer-centric BFS over active endorsement awards, with a server cap). P1 Explore "Endorsed users" filter. Reconstructable via client BFS (forward awards-by-issuer already works), but a server resolver is far cheaper and gives provenance + truncation semantics for free.
9 Denormalize issuer + response onto awards On the award node, inline issuer{ handle, displayName, avatarCid, pds } and the recipient's latest response{ state, weight, createdAt }. P2 Kills the N+1 profile/response fan-out on the endorsements panel's first paint. Quality-of-life once #1 lands.
10 isOrganization flag on actor profile Add a derived isOrganization: BooleanFilterInput to AppCertifiedActorProfileWhereInput. P2 Lets the explore People/Org toggle filter in one query instead of client-side intersecting with appCertifiedActorOrganization. Workaround exists, so lower priority.
11 Case-insensitive matching (or normalized type) Add eqi to StringFilterInput, or normalize the collection type discriminator at ingest ("project" / "list:endorsements"). P2 Today type:{eq:"project"} misses mixed-case records ("Project"/"PROJECT"). Affects project listings + counts. Normalization upstream is the cleanest fix.
12 Denormalized actorProfile(did) with handle + typed search Add actorProfile(did){ handle, displayName, description, avatarCid, bannerCid } (incl. resolved handle); and let the top-level search() return typed nodes or expose a search arg per connection. P2 DID-resolution fast-path (currently flag-off; legacy path works) and typed full-text search without re-fetching from the generic record connection. Pure latency/ergonomics wins.

If only the four P0 items shipped, certified-app could run on stock Hyperindex with every feature present — degraded only in latency (extra round-trips / client joins) on the P1–P2 items, not in capability.

Bottom line (verified). The deployed Hyperindex is the same ATProto indexer and covers far more than the code comments implied — once queries are rewritten to its native syntax (externalLabels:{has,none} for labels, did:{eq,in} for authors/issuers, sortBy, and the top-level search()). Of the ~27 operations: ~9 work directly or with a pure rewrite; ~9 work degraded (aliased …ByUri fan-out instead of uri.in; client-side intersects for People/Org; case-sensitive type:"project"; client-side badgeType joins; BFS for the trust graph). The genuine blockers are narrow but real: (1) badge awards can't be filtered by recipient (presence-only subject) → kills received-endorsements and its count; (2) no contributor-DID filter; (3) no activity→collection (itemUri) filter; (4) no followerEvents union with a single cursor; and (5) the entire notifications service is a separate component. The fork mostly exists to denormalize joins and add three reverse/derived indexes the base schema doesn't expose — recipient-keyed awards, contributor, and itemUri — plus the feed/closure/notification resolvers.
