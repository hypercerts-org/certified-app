### 1. Global X-Frame-Options: DENY + CSP frame-ancestors 'none' break the shipped /embed/board third-party embed feature

- **id / dimension:** `next-embed-frame-headers-block-embeds` · nextjs
- **severity / effort / regression-risk:** High / S / low
- **location:** `next.config.ts:27`
- **evidence:** headers() applies to `source: "/(.*)"` and sets `{ key: "X-Frame-Options", value: "DENY" }` (line 27) plus CSP `... frame-ancestors 'none'; ...` (lines 61-62), for BOTH prod and dev. There is no embed-specific override (grep of next.config.ts finds no /embed header rule; there is no middleware.ts). Yet `src/app/embed/board/[...slug]/page.tsx` is documented as 'Public embed route ... Renders bare ... so it drops cleanly into a third-party iframe', and `src/components/contributor-board/share-embed-dialog.tsx:20` hands users `<iframe src="${origin}/embed/board/${did}/${rkey}" ...>` to paste on their own sites. X-Frame-Options: DENY and frame-ancestors 'none' both forbid all cross-origin (and same-origin) framing, so that iframe is refused by every browser.
- **failure scenario:** A creator opens a contributor board, clicks Share, copies the iframe snippet, and pastes it into their own website. In production the embedded frame renders blank / 'refused to connect' because the /embed/board response carries X-Frame-Options: DENY and frame-ancestors 'none' — the entire embed feature is silently non-functional for its sole purpose.
- **fix:** Stop sending X-Frame-Options: DENY and frame-ancestors 'none' for /embed. Split headers(): keep the DENY + frame-ancestors 'none' rule on a source that excludes embed (e.g. `source: "/((?!embed/).*)"`), and add a second rule `source: "/embed/:path*"` that omits X-Frame-Options entirely and sets CSP `frame-ancestors *` (or an explicit partner-origin allowlist). Add a smoke assertion that a GET to /embed/board/x/y carries no X-Frame-Options header.

### 2. TipTap editor (~9.7 MB dep tree) is statically imported into read-heavy route bundles though it only renders in edit mode

- **id / dimension:** `bundle-tiptap-static-import` · perf-data
- **severity / effort / regression-risk:** High / M / low
- **location:** `src/components/feed/activity-detail.tsx:82`
- **evidence:** leaflet-editor.tsx statically imports `@tiptap/react`, `@tiptap/starter-kit`, `@tiptap/extension-link`, `@tiptap/extension-placeholder` at module top (leaflet-editor.tsx:5-8), pulling in the full prosemirror stack (node_modules @tiptap = 6.6M + prosemirror-* ~3M on disk). `LeafletEditor` is imported statically at 8 sites — activity-detail.tsx:82, project-detail.tsx:40, src/app/[actor]/page.tsx:33 (all high-traffic READ surfaces), plus create/new/edit routes. In every read surface it is only *rendered* in edit mode: activity-detail.tsx:1222 (`editing ? <LeafletEditor>`), project-detail.tsx:1314, [actor]/page.tsx:552 (`editing && sidebarIsOrg`). No dynamic wrapper exists (src/components/leaflet has no *-dynamic file). By contrast leaflet (map-dynamic.tsx) and react-force-graph-2d (visualization.tsx:16) are correctly behind next/dynamic — TipTap is the one heavy dep that is not.
- **failure scenario:** Any anonymous visitor opening a cert, project, or profile page downloads the entire TipTap + prosemirror bundle in the route's JS even though they can never edit — inflating first-load JS and TTI on the app's most-visited read pages.
- **fix:** Add a `leaflet-editor-dynamic.tsx` wrapper: `const LeafletEditor = dynamic(() => import('./leaflet-editor'), { ssr: false, loading: () => <EditorSkeleton/> })`, re-export the props type, and switch the 8 import sites to it. TipTap then loads only when a user actually enters edit mode, removing ~150-200 KB gzip from the profile / activity-detail / project-detail first-load bundles.

### 3. Explore result list re-sorts and re-renders every row on each search keystroke (unmemoized rows, no virtualization, unbounded via loadMore)

- **id / dimension:** `perf-explore-results-wholesale-rerender` · perf-render
- **severity / effort / regression-risk:** High / M / low
- **location:** `src/components/explore-page/explore.tsx:1997`
- **evidence:** The search box lives in ExploreMain as local state (`const [localQuery, setLocalQuery] = useState(search)` at 694; `<Input value={localQuery} onChange={(e)=>setLocalQuery(e.target.value)}>` at 755). `<ResultsArea>` (927) is a sibling in the same component, so every keystroke re-renders ResultsArea. ResultsArea sorts in the render body — `certs = sortCerts(certs, sort)` (1997), `actors = sortUsers(...)` (1928), `projects = sortProjects(...)` (1959) each do `[...list].sort()` allocating a new array — then `.map`s over it. The list-view row components it renders are NOT memoized: CertListRow (2007), AccountListRow (1935), ProjectListRow (1971), ExploreUserCard (1948), ExploreProjectCard (1985), FundingReceiptRow (1918) are all plain `export default function` (only ActivityCard in the gallery certs view is `memo`). Cleaner still: extract the search `<Input>` + debounce into its own component so keystrokes never touch the ResultsArea subtree.

### 4. Unauthenticated SSRF: attacker-controlled host+port in .well-known handle resolution (no IP filter)

- **id / dimension:** `sec-ssrf-wellknown-handle` · sec-inject
- **severity / effort / regression-risk:** High / S / low
- **location:** `src/lib/atproto/did.ts:179`
- **evidence:** resolveHandleViaWellKnown() fetches `https://${handle}/.well-known/atproto-did` with the ONLY validation being `handle.includes('.') && !/\s/.test(handle)` (line 174-175). Unlike resolvePdsUrl, it runs NO isAllowedPdsUrl / IP-range check. `handle` is fully client-controlled and reaches this via resolveInputToDid (resolve-core.ts:1187) from the unauthenticated GET /api/resolve-did?handle=… and POST /api/resolve-dids. Because a handle only needs a dot and no whitespace, values like `169.254.169.254`, `internal.svc:8080`, or `10.0.0.5` all pass, so the server issues `https://169.254.169.254/.well-known/atproto-did` etc. — arbitrary host AND port. The bsky-appview resolve runs first but returns null for a bogus handle, so control always falls through to this branch. fetch uses the default redirect:follow, so the target can also 302 onward.
- **failure scenario:** Unauthenticated attacker calls GET /api/resolve-did?handle=10.0.2.15:6379 (rate-limited only at 60/min/IP); the server makes an outbound request to the internal Redis/host, enabling internal-network port scanning and reachability probing (timing/error-shape oracle), and can exfiltrate any endpoint whose body starts with `did:`.
- **fix:** Validate `handle` as a real hostname before interpolation: reject anything containing `:`, `@`, `/`, or `%`, require it to match a DNS-name regex (labels of [a-z0-9-] separated by dots, TLD present), then build a URL and run it through isAllowedPdsUrl() (the same gate resolvePdsUrl uses). Add `redirect: "error"`. This mirrors the anti-SSRF pattern already used in onboarding/clone-blob.

### 5. SSRF: PDS proxy fetches follow redirects, so an allowed PDS host can 302 the server to internal targets

- **id / dimension:** `sec-ssrf-pds-redirect-follow` · sec-inject
- **severity / effort / regression-risk:** High / S / low
- **location:** `src/app/api/xrpc/[...method]/route.ts:219`
- **evidence:** proxyPublicGetRecord (fetch @219), proxyPublicListRecords (@267) and proxyPublicGetBlob (@309) fetch `${targetPds}/xrpc/…` with default `redirect: "follow"`; the same is true of getCertsProfile in resolve-core.ts:267 and establish() in group-account-session.ts. isAllowedPdsUrl only validates the INITIAL serviceEndpoint host, and the DID owner fully controls that endpoint (any did:plc or did:web can advertise a serviceEndpoint on a real external host). That host can then reply `302 Location: http://169.254.169.254/…` or `https://127.0.0.1:8443/…` and undici follows it, completely bypassing the host allowlist. The GET handler (line 343) is reachable unauthenticated for com.atproto.repo.getRecord/listRecords/sync.getBlob (PUBLIC_READ_METHODS), and the JSON/blob response body is returned to the caller — a full read SSRF with exfiltration.
- **failure scenario:** Attacker registers did:plc:xxxx with serviceEndpoint https://attacker.example (passes filter), hosts a 302 to http://169.254.169.254/latest/meta-data/… then calls GET /api/xrpc/com/atproto/repo/getRecord?repo=did:plc:xxxx&collection=x&rkey=y; the server fetches the internal target and returns the body to the attacker.
- **fix:** Set `redirect: "error"` on all upstream PDS fetches (proxyPublicGetRecord/ListRecords/GetBlob, resolve-core getCertsProfile, group-account-session establish). If redirects must be supported, follow manually and re-run isAllowedPdsUrl on every hop's resolved host.

### 6. Core pages render a nested second <main> landmark inside the layout's <main>

- **id / dimension:** `a11y-nested-main-landmarks` · a11y
- **severity / effort / regression-risk:** Medium / S / low
- **location:** `src/components/explore-page/explore.tsx:726`
- **evidence:** The root layout wraps every route in `<main id="main-content">` (src/app/layout.tsx:178, `<AppShell>{children}</AppShell>`). The page bodies then render their OWN `<main>`: explore.tsx:726 and :1244 `<main className="explore__main">`, and home.tsx:101 `<main className="home__main">`. That produces two nested `<main>` landmarks per page. The HTML spec allows only one non-hidden <main>; screen-reader landmark navigation (rotor / 'D' key) then reports two 'main' regions with no distinction, and the skip-link target semantics are muddied.
- **failure scenario:** A screen-reader user on /home or /explore navigates by landmarks and lands on two 'main' regions (the layout wrapper and the page's inner one), with the real content nested a level deeper than the announced top-level main.
- **fix:** Change the inner page-level `<main className="explore__main">` / `<main className="home__main">` to a `<div>` (or `<section aria-label=…>`). CSS targets these by class only (grep found no `main.explore__main`/`main.home__main` tag-qualified selectors), so the ≥1300px visual baseline is unchanged. WCAG 1.3.1.

### 7. Primary pages have no programmatic h1 — the page title is a non-heading <div>

- **id / dimension:** `a11y-page-title-not-heading` · a11y
- **severity / effort / regression-risk:** Medium / S / low

### 8. Create-flow field errors are not programmatically tied to their inputs (missing aria-describedby / aria-invalid)

- **id / dimension:** `a11y-form-error-association` · a11y
- **severity / effort / regression-risk:** Medium / S / low
- **location:** `src/app/groups/create/page.tsx:513`
- **evidence:** groups/create uses raw `<input aria-label="Display name">` (497), `<input aria-label="Handle">` (551), `<input aria-label="Group email">` (587) with their errors in detached `<p role="alert">` nodes (nameError 513, handleError 571, emailError 604) — the inputs carry NO `aria-invalid` and NO `aria-describedby`, so a user returning to the field gets no invalid state and the error text is not associated. create/page.tsx has the same detached-error pattern for the end-date (aria-invalid at 703, error `<p role="alert">` at 709 with no id/describedby), the contributor weight (aria-invalid 1044, error 1071), and the contributor identity field. ### 9. Home-feed loadMore has no abort signal or generation guard, so a filter toggle mid-pagination appends stale, filter-violating events

- **id / dimension:** `correctness-homefeed-loadmore-stale-append` · correctness
- **severity / effort / regression-risk:** Medium / M / low
- **location:** `src/hooks/use-home-feed.ts:325`
- **evidence:** The initial `load()` threads its AbortController signal into both `fetchFollowerEvents` and `hydrateFeedEvents` and guards every setState with `if (signal.aborted) return` (lines 271-285). `loadMore` does NOT: it calls `fetchFollowerEvents({authors, first, after: snap.cursor, sortBy})` (lines 325-330) and `hydrateFeedEvents(page.events, {...})` (lines 331-334) with no signal, and its success `setState((prev) => { ...events: [...prev.events, ...append] })` (lines 338-350) has no abort/generation check. The effect cleanup (lines 393-400) only aborts the initial `controller` and the INVALID_CURSOR `recoveryControllerRef` — it cannot cancel an in-flight normal loadMore.
- **failure scenario:** User scrolls to trigger loadMore; while the two round-trips are in flight they toggle a quality tier in the filter popover. `excludeKey` changes, the effect re-runs `load()` which replaces state with the newly-filtered page. The in-flight loadMore then resolves and its `setState((prev) => ...append...)` appends events fetched under the OLD cursor into the fresh list. Result: rows that don't satisfy the active filter appear in the feed and persist until a full reload; the same uncancelled setState also fires after unmount if the user navigates away.
- **fix:** Give loadMore its own AbortController tracked in a ref (or reuse a generation counter). Pass its signal to both fetchFollowerEvents and hydrateFeedEvents, guard the success setState with `if (signal.aborted) return`, and abort it in the effect cleanup alongside the recovery controller.

### 10. useUserIndexerActivities paginates without URI de-duplication, producing duplicated rows and duplicate React keys

- **id / dimension:** `correctness-user-indexer-activities-no-dedupe` · correctness
- **severity / effort / regression-risk:** Medium / S / low
- **location:** `src/hooks/use-user-indexer-activities.ts:221`
- **evidence:** `mergeBucket` blindly concatenates: `records: [...prev.records, ...data.records]` (line 221) with no seen-set filter. - **failure scenario:** The indexer returns a record at a cursor boundary that was already present on the prior page (a new insert shifts the window, or the cursor is inclusive). - **fix:** In mergeBucket, build `const seen = new Set(prev.records.map(r => r.uri))` and append only `data.records.filter(r => !seen.has(r.uri))`, matching the sibling hooks.

### 13. Root `/` is a client-only spinner that fetches session then client-redirects, though the session cookie is server-readable

- **id / dimension:** `next-root-client-redirect-flash` · nextjs
- **severity / effort / regression-risk:** Medium / M / medium
- **location:** `src/app/page.tsx:26`
- **evidence:** src/app/page.tsx is `"use client"` and renders only a LoadingSpinner; its useEffect (lines 26-33) waits for `useAuth()`, which resolves via a client fetch to `/api/auth/session` (auth-context.tsx:53), then `router.replace('/home')` or `router.replace('/welcome')`. The auth source of truth is an httpOnly cookie readable server-side via `getSessionDid()` (src/lib/auth/session.ts:46) — the same call `/api/auth/session` makes. So `/`, the highest-traffic entry (and robots-allowed), ships the full client bundle, mounts providers, does a network round-trip, and flashes a spinner purely to compute a redirect the server already has the inputs for.
- **failure scenario:** Every first visit to certified.app loads the entire app JS, mounts AuthProvider, fetches /api/auth/session, and shows a spinner for the round-trip before redirecting — added latency and a visible flash on the busiest route; crawlers see a blank spinner page and must follow a client-side redirect.
- **fix:** Convert src/app/page.tsx to a Server Component (drop "use client"): `const did = await getSessionDid(); redirect(did ? '/home' : '/welcome')`. This runs as a 307 before any bundle loads — no spinner, no round-trip, crawler-friendly. (A middleware.ts redirect is the equivalent alternative; a dedicated server page is simpler and avoids adding edge middleware just for this.) Redis presence is an authoritative-enough proxy for which landing page; /home re-verifies the OAuth session and bounces if revoked.

### 14. generateMetadata for profile/record pages does uncached upstream fetches on every request

### 16. useProjectItems fans out one PDS getRecord per project item instead of using the indexer's batch-by-URI query

- **severity / effort / regression-risk:** Medium / M / medium
- **location:** `src/hooks/use-project-items.ts:95`
- **evidence:** useProjectItems (use-project-items.ts:95-142) does `Promise.all(uriList.map(...authFetch('/api/xrpc/com/atproto/repo/getRecord?...')))` — one XRPC round-trip per cert in the project, on the project-detail page.
